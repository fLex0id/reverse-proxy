# Архитектура rp

`src/` содержит исходники VPS-1 и шаблоны для VPS-2. Порядок загрузки
задаёт `src/modules.list`. Диспетчер запускает инициализацию из
`src/main/init.sh`, подключает определения, затем вызывает `main "$@"`.
Модули Bash объявляют функции. Пути, глобальные массивы, параметры Bash и
оформление инициализируются в точке входа.

## Связи между модулями

| Модуль | Ответственность и вызываемые функции других модулей |
| --- | --- |
| `lib/core` | UI, вопросы, чтение и атомарная запись конфигурации. Общая зависимость CLI и операций. |
| `lib/sys` | ОС, пакеты, firewalld, SELinux, локальный сетевой адрес. Используется установкой VPS-1 и выдачей блока. |
| `lib/fetch` | Загрузка, списки релизов, определение адреса выхода и хэшей закреплённых релизов. Использует `cf` и UI. |
| `lib/python` | Вызов генератора и публикация `rp.py`. Генератор создаёт конфигурации обеих ролей, блок, маршруты, экспорт и QR. |
| `mod/vps1` | Установка, идентичность, бинарники, юниты, применение и откат конфигурации. Вызывает `sni_choose`, `ru_update`, `py`, `self_install`, `unit_up`, `route_*`. |
| `mod/sni` | Выбор и диагностика кандидатов SNI. Вызывается установкой и командой `sni`. |
| `mod/ru`, `mod/clients`, `mod/dns` | Изменение списков РФ, клиенты WG, DNS и DoH соответственно. Используют генератор, конфигурацию и `vps1_apply` / `vps1_set`. |
| `mod/delivery`, `vps2/templates` | Генерация блока, частей и HTTPS-ссылки. `block_make` вызывает `vps2_files` → `transaction_source`, затем `py bundle`, `vps2_installer` и при необходимости `py chunk`. |
| `mod/control`, `mod/route` | SSH и проверки управляющего канала, сверка активного режима и API маршрутизации. `route_sync` → `vps2_read`. `ssh_args` использует подтверждённый транспорт и состояние маршрута. |
| `mod/transports`, `mod/push` | Выбор транспорта, запрос режима и передача конфигурации. `cmd_tunnel` → `route_prepare`, `push_ssh`, `route_pin`. `cmd_push` → `block_make`, `push_ssh`, `push_wait` → проверки и подтверждение через `vps2_run`. |
| `mod/diagnostics` | T1–T8 VPS-1, состояние, цепочка проверки, перезапуск и удаление. `cmd_test` → функции контроля/маршрута, `doh_test`, `failclosed_static`. |
| `mod/update`, `main/distribution` | Самообновление, миграция, обновление компонентов и локальная публикация пакета. `self_upgrade` → `self_fetch` → новая точка входа `migrate`. `cmd_migrate` → `migration_run` → Python-супервизор → `migrate_apply`. |
| `mod/menu`, `mod/cli` | CLI, меню, блокировка и маршрутизация команд к операциям. |

Связи `vps1 ↔ ru` и `route ↔ control` отражают существующий обмен между
операциями: установка получает списки, команда изменения списков применяет
конфигурацию, а синхронизация запрашивает состояние через управляющий канал.
Порядок подключения не служит порядком вызова: выполнение начинается после
загрузки определений.

Во вложенном VPS-2 цепочка выглядит как `watch.sh → rp _fn →
tr_start / func_ok / t1_check / t2_check / t3_check`. Тела сторожа, CLI и установщика хранятся в `src/vps2/runtime/` и
подставляются сборкой в прежние шаблоны. Юниты и
транзакционный Python входят в сгенерированный блок. Его алгоритмы загрузки,
проверок SHA-256, разбиения, применения и подтверждения взяты из `lab.23`.
Развёрнутый VPS-2 получает собственный CLI и сторож из блока.

## Выпуск и установка

`tools/build.sh --output DIR` собирает загрузчик, архив, резервный монолит,
совместимый загрузчик для `lab.23` и `SHA256SUMS`. Порядок файлов, uid/gid,
права и поля времени архива фиксированы. Python 3 для сборки использует
стандартную библиотеку. `tools/package-release.py` добавляет SHA коммита и
проверяет совпадение закоммиченного `rp.sh` c результатом сборки.

Загрузчик берёт архив по версии релиза. Ожидаемый SHA-256 зашит при сборке.
Данные извлекаются после проверки хэша, в отдельный временный каталог.
Повторные попытки и зеркало проверяются по тому же хэшу. При установке команда
под общей блокировкой публикует полное дерево через переименование в
`/usr/local/lib/rp/releases/<id>`, затем атомарно заменяет
`/usr/local/bin/rp`. Предыдущий диспетчер указывает на предыдущее дерево.
При миграции публикация происходит внутри существующего снимка VPS-1.
Восстановление использует старый диспетчер, который может подключить
восстановленное дерево и выполнить прежнюю проверку готовности.

Установленный диспетчер открывает только локальные файлы. Обращения к сети
выполняют команды, для которых это требуется, например `rp update`.
`rp-single.sh` остаётся самодостаточным запасным вариантом. Удаление модульного
VPS-1 оставляет доступную команду `rp` как монолит, как и историческое удаление.

Проверка `self_ok` сохраняет прежний контроль монолита и проверяет метаданные
и синтаксис новых точек входа. Компактный загрузчик не проходит порог 32 КиБ в
уже выпущенном `lab.23`. Для одношагового перехода через старый `rp update`
предназначен артефакт `rp-legacy-update.sh`. Он несёт исторические проверяемые
определения и скачивает тот же пакет по тому же SHA-256. При запуске новой
версии из потока доступна обычная команда `migrate` или пункт миграции в меню.

## Как добавить модуль

1. Выберите границу по ответственности и добавьте `lib/*.sh`, `mod/*.sh` или
   соответствующий исходник в `vps2/`. Зависимости отражайте в таблице.
2. Добавьте путь в `src/modules.list`. Поместите инициализацию в
   `src/main/init.sh`. Для встроенного в шаблон фрагмента Python добавьте
   исходник в `src/py/snippets` и укажите `@PY:имя@` в нужном месте.
3. Соберите через `tools/build.sh`, обновите корневой `rp.sh` и запустите
   `tools/static-check.py`, `tools/compare-functions.sh --dist DIR` и
   `python3 -m unittest discover -s tests -v`. Сравнение проверяет оба формата
   VPS-1, весь встроенный Python и генерируемые шаблоны VPS-2.
