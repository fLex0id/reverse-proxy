# PRIORITY 0 — неизменяемые требования проекта `rp.sh`

**Статус:** утверждено владельцем проекта, 2026-11-21.  
**Область действия:** все версии `rp.sh`, задания Codex T0–T7, рефакторинг, выпуск релизов, миграции, установка Teleport и эксплуатация.  
**Обязательное действие:** перечитывать этот файл **перед каждым заданием, изменением архитектуры, ревью и приёмкой**.

> Этот документ — спецификация требований владельца, а **не утверждение о том, что текущее состояние программы уже им соответствует**. Соответствие необходимо доказывать тестами на конкретном релизе.

## P0. Главная цель

Главная цель `rp.sh` — построить **защищённый туннель или несколько туннелей с максимально возможной скрытностью от ТСПУ**, используя устойчивую и реалистичную **мимикрию под легитимный сетевой трафик**. Доступность должна достигаться без демаскирующих побочных эффектов.

- **Приоритет 0 выше любых иных улучшений:** производительности, скорости, сложности архитектуры, удобства интерфейса, рефакторинга, обновлений, вспомогательных функций и интеграции Teleport.
- Использовать **зрелые, обоснованные и практически проверяемые** методы. Не внедрять сомнительные или экспериментальные техники лишь ради новизны.
- Определять эффективность транспортов **наблюдениями и воспроизводимыми измерениями**, не считать теоретическую «скрытность» доказанной.
- **Не исследовать, не искать и не исправлять внутренние уязвимости самих протоколов** в рамках проекта. Это вне области работ. Ошибки `rp.sh` в маршрутизации, DNS, политике доступа, конфигурации, failover и защите от утечек остаются в области ответственности проекта.
- **Безопасность маршрутизации и запрет утечек — обязательные ограничения**, которыми нельзя пожертвовать ради видимой доступности.

## P0.1. Неизменяемая топология и модель соединений

```text
WG-клиент (включая OpenWrt)
    │  WireGuard: единственный не-маскируемый для ТСПУ участок
    ▼
VPS-1 (в РФ; приём WG-клиентов, маршрутизация, политики, failover)
    ▲  VPS-2 ИНИЦИИРУЕТ исходящее соединение;
    ║  ВЕСЬ межсерверный пользовательский, управляющий и SSH-трафик
    ║  передаётся только через защищённый маскируемый туннель
    ▼
VPS-2 (зарубежный выход в Интернет; прямой доступ из РФ заблокирован)
    │
    ▼
Зарубежный Интернет: внешний адрес клиента = публичный IPv4 VPS-2
```

Нормативные требования:

1. Все WG-клиенты, включая OpenWrt, выходят к зарубежным ресурсам **с публичного IP VPS-2**, а не VPS-1. Предположение о блокировке прямого доступа из РФ к VPS-2 — эксплуатационное требование, которое проверяется в целевой сети.
2. **VPS-2 самостоятельно устанавливает соединение с VPS-1.** VPS-2 не открывает доступных из Интернета входящих портов для работы комплекса. Возвратные пакеты для уже установленных исходящих соединений допустимы; это не разрешение открыть публичный listener.
3. **SSH к VPS-2 доступен только через установленный туннель**; прямой SSH с VPS-1 или из Интернета не используется. Внеполосная консоль провайдера для аварийного восстановления не является прямым сетевым SSH-каналом и допустима.
4. Весь обмен VPS-1 ↔ VPS-2, относящийся к комплексу (клиентские данные, управление, проверки состояния, SSH), проходит **только внутри ТСПУ-устойчивого маскируемого туннеля**.
5. Между VPS-1 и VPS-2 **запрещены самостоятельные прямые соединения WireGuard, SSH или другого VPN** в обход основного замаскированного транспорта. WireGuard допустим только на участке **клиент → VPS-1**.

**Следствие:** любые альтернативные архитектуры с исходящим установлением межсерверного соединения с VPS-1 на VPS-2, публичным SSH-портом VPS-2, прямым WG между серверами или выходом зарубежного трафика с VPS-1 нарушают P0.1, даже если они проще или быстрее.

## P0.2. Приоритет транспортов определяется скрытностью, не скоростью

Базовый порядок предпочтения для **автоматического режима** (согласно решению владельца):

1. Reality + XHTTP **packet-up**;
2. Reality + XHTTP **stream-up**;
3. Hysteria2 **без обфускации**;
4. Hysteria2 **с Salamander**.

Это **исходная политика**, а не научно доказанный универсальный рейтинг обнаруживаемости. Названия/параметры конкретных реализаций должны быть проверены на применяемых версиях Xray/Hysteria2. Изменение порядка возможно **только по подтверждённым измерениям и явному решению владельца**. Система не должна автоматически переставлять транспорты по пропускной способности, задержке или результатам speedtest.

При равной приемлемой скрытности допускается учитывать надёжность. Рост скорости сам по себе не является основанием менять порядок.

## P0.3. Два режима выбора и обязательный failover

- **Автоматический режим:** обнаруживает реальную потерю передачи данных (в том числе «рукопожатие успешно, полезный трафик остановился»), исключает неработающий транспорт и переключается на доступный согласно политике P0.2.
- **Ручной режим:** владелец явно выбирает и закрепляет транспорт. При его отказе **не происходит несанкционированного переключения** на иной транспорт или прямой выход; действует fail-closed.
- Изменения методов диагностики, таймеров, частоты проб и keepalive не должны увеличивать заметность соединений для ТСПУ без обоснования измерениями.
- После изменения режима, обновления, перезагрузки и отката сохраняются выбранная политика, закрепление и состояние клиентов, если владелец не потребовал иного.

## P0.4. Жёсткое разделение маршрутизации и DNS, отсутствие утечек

1. **Зарубежные домены и зарубежные IP-адреса:** клиентский трафик направляется **только через туннель и VPS-2**. При невозможности установить защищённый маршрут запрос должен быть заблокирован, **никогда** не переключён на прямой Интернет.
2. **Российские маркетплейсы, банки, государственные сайты и ведомства:** обслуживаются **только напрямую**, в обход зарубежного туннеля. Прямой маршрут реализуется через VPS-1, а не через VPS-2.
3. **DNS для зарубежных имён не уходит напрямую в WAN/к провайдеру**, не покидает разрешённый туннель ни обычным DNS, ни DoT/DoH, ни иным разрешением имён. При падении туннеля запрещён прямой fallback DNS для зарубежных имён. Служебное разрешение имён, необходимое исключительно для установления самого транспорта, требует отдельно документированной политики и не должно превращаться в канал утечки клиентских DNS-запросов.
4. Маршрутизация и DNS-политика обязательны для IPv4 и IPv6: если безопасный путь для семейства адресов не реализован, это семейство должно быть заблокировано. Нельзя допускать прямого выхода по IPv6 при корректном IPv4-туннеле.
5. При неопределённой классификации адреса/домена безопасное поведение — **не направлять его напрямую**. Не использовать нестабильные предположения о географической принадлежности CDN или DNS-ответа в качестве основания для обхода защиты.

**Требование fail-closed распространяется на сбои транспорта, DNS, рестарт служб, переключение, обновление и откат.** Прямой маршрут к разрешённым российским ресурсам остаётся допустимым только при строгом соответствии правилам P0.4.

## P0.5. Реализация может эволюционировать, семантика — нет

Методы реализации допускается заменять более современными, надёжными и технологичными подходами: модулями, библиотеками, механизмами маршрутизации, проверками состояния, форматами конфигурации, сборкой единого `rp.sh`. Однако **наблюдаемое поведение и инварианты P0–P0.4 должны сохраняться**. Ни рефакторинг, ни интеграция Teleport, ни переход на другой механизм обновления не дают права изменять их молча.

Если реализация требует отказаться от любого пункта, **Codex останавливается**, фиксирует конкретное противоречие и запрашивает решение владельца. Нельзя скрывать нарушение за «улучшением архитектуры».

### Независимость Teleport

Опциональный Teleport устанавливается **после успешной установки ядра `rp.sh`**, отдельно от транспорта и failover. Репозиторий пакетов — `https://flex0id.github.io/reverse-proxy/` (подписанные APT/RPM индексы), ожидаемый GPG fingerprint: `95AB1A0D022288C96B135E395D6220FDB9C74356`. После первоначальной установки обновления идут **штатно через `dnf update` / `apt update && apt dist-upgrade`**. Обновление/удаление `rp.sh` не затрагивает установленный Teleport. Teleport не должен изменять сетевые политики P0.1–P0.4.

## Приёмочные проверки P0 (не заменяются успешным рукопожатием)

Codex обязан документировать и, где есть стенд, воспроизводимо проверять следующие наблюдения:

| Контроль | Критерий |
| --- | --- |
| Топология | VPS-2 инициирует соединение; на его публичном интерфейсе нет доступных входящих сервисов комплекса; SSH к VPS-2 работает только через туннель |
| Внешний IP | Для зарубежного тестового адреса WG-клиент (включая OpenWrt) имеет выходной IP VPS-2 |
| Транспорт | Полезные данные продолжительно передаются в обе стороны; отсутствие прогресса вызывает failover в автоматическом режиме |
| Приоритеты | Автоматический выбор соблюдает P0.2, а не сортировку по скорости |
| Ручной режим | Закреплённый транспорт не заменяется другим автоматически |
| Зарубежный трафик | Без туннеля — DROP/REJECT согласно безопасной политике; прямого выхода с VPS-1 нет |
| Российские ресурсы | Контрольные сайты банков, маркетплейсов и госорганов используют прямой маршрут |
| DNS | Зарубежные домены разрешаются без прямых запросов в WAN; при отказе туннеля нет прямого DNS-fallback |
| IPv6 | При отсутствии безопасной реализации нет прямой IPv6-утечки |
| Перезапуск/обновление | Защищённые правила соблюдаются и в промежуточных состояниях |

**Стандарт доказательства:** логи, трассировки/счётчики, сетевые измерения и воспроизводимые тесты на конкретной конфигурации. Эмуляция блокировок не доказывает невидимость для реального ТСПУ; результаты на реальных линиях должны рассматриваться отдельно. Неиспытанное помечать `NOT_TESTED`, не писать `PASS`.

## Как применять к задачам Codex

1. Перед **каждым** T0–T7 прочитать этот файл и перечислить применимые P0-инварианты в плане.
2. Проверить предложенные изменения на конфликт с P0 прежде, чем менять код.
3. После выполнения приложить матрицу `P0.x → тест → результат / NOT_TESTED` и перечислить все изменения сетевого поведения.
4. Если есть риск нарушения P0, не пытаться молча компенсировать его ускорением, удобством или иной функциональностью: остановиться и запросить решение владельца.
5. Документы стороннего ИИ (`docs/codex-guidance/`) являются **совещательными**, а не более высоким источником требований. При расхождении с этим файлом приоритет у **решений владельца в PRIORITY-0.md**.
6. Перед новой задачей ответственный консультант рекомендует модель Codex и новую/продолжаемую сессию, а при существенной технической неопределённости может запросить внешнюю экспертизу.
