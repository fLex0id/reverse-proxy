# T5. Разбиение Bash на модули

**Тип:** рефакторинг; перенос функций без изменения.
**База:** тег `task-4-accepted`. Ветка `task/5-split-bash`.
**Читать:** `AGENTS.md`, `TECHNICAL-DETAILS.md` §2, §9, `DECISIONS.md`.

## Цель

Разделить Bash-часть на модули `core`, `system`, `net`, `roles-vps1`, `roles-vps2`, `cli` в явном порядке `src/modules.list`.

## Сделать

1. Для каждой функции определить модуль **по зависимостям**, а не по названию. Письменная таблица «функция → модуль → основание» в записке; спорные — в «Открытые вопросы».
2. Правило: **на верхнем уровне модуля только определения**; никакого кода, выполняющегося при подключении. Единственная точка входа — `main`. Добавить статическую проверку.
3. Внутрисистемные зависимости между модулями — только «вниз»: `cli` → `roles` → `net`/`system` → `core`. Циклы запрещены; добавить проверку.
4. Карта «модуль → тесты» (`docs/MODULE-TEST-MAP.md`): какие тесты и сценарии `lab/` должны проходить при изменении модуля. Используется для привязки приёмки к хэшам модулей (§9).
5. Разбиение выполнять **малыми шагами**: один модуль за коммит; после каждого — равенство `dist/rp.sh` эталону по поведению (см. ворота).

## Ворота

- Бинарного равенства с эталоном здесь **не будет** (порядок кода изменился). Вместо него:
  - золотые файлы без изменений; тест CLI без изменений;
  - 155+ тестов, число не уменьшилось, ожидания не менялись;
  - манифест состояния (T4) равен эталону на откатанном снимке;
  - T1–T3 четырёх транспортов — один проход (`NOT_RUN`, если стенда нет);
  - матрица T1 (`tspu_matrix`) на сокращённом наборе: по одному повтору каждого сценария — без регрессии по сравнению с эталоном.
- Статические проверки правила «только определения» и «зависимости вниз» проходят.

## Нельзя

Менять поведение, добавлять функции, переименовывать команды и сообщения, менять тайминги и параметры транспортов.
