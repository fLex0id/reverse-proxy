# TECHNICAL-DETAILS.md — предлагаемая реализация

Ссылки на строки относятся к `rp.sh` на ревизии `850ce47`. Это **предложение**, а не готовое решение: каждый пункт, помеченный «проверить», нужно подтвердить на нужной версии ОС или документации.

## 1. Принципы

1. **Сначала доказуемая эквивалентность, потом изменения.** Рефакторинг не меняет поведение; это проверяется механически (побайтное равенство сборки, золотые файлы, манифест состояния), а не стендовыми прогонами.
2. **Python остаётся читаемым текстом внутри `rp.sh`.** Пользователи запускают `bash <(curl …)` от root; они вправе прочитать, что исполняется.
3. **Минимум зависимостей.** Только то, что уже есть на Rocky 9/10: Bash, Python 3.9+, OpenSSL, coreutils, systemd.
4. **Один способ делать вещь.** Два движка транзакций объединяются; пути, которые считаются «своими», перечисляются явно.

## 2. Целевая структура репозитория

```text
VERSION                    # единственное место версии: 1.3.0-rc.1
src/
  modules.list             # явный порядок модулей, без шаблонов
  bash/
    core.sh                # конфигурация, состояние, журнал, замок, UI-примитивы
    system.sh              # ОС, пакеты, systemd, firewalld, sysctl
    net.sh                 # транспорты, маршруты, nft, DNS/DoH, списки РФ
    roles-vps1.sh
    roles-vps2.sh          # установка, push, apply, сторож
    cli.sh                 # разбор команд, меню, диагностика
    integrations/
      teleport.sh          # только установка Teleport (T7)
      teleport.meta        # версия, URL, SHA256 — данные, не код
  python/rp/
    __init__.py  __main__.py
    gen.py                 # генераторы конфигураций (сейчас встроенный rp.py)
    txn.py                 # ОДИН движок транзакций (сейчас transaction.py + migration.py)
    state.py               # снятие манифеста состояния, schema_version
tools/
  build.py                 # сборщик, только стандартная библиотека
  static-check.py
tests/  lab/  reports/
dist/rp.sh                 # результат сборки, коммитится
```

Обоснование числа модулей (семь вместо десяти): в Bash нет настоящей инкапсуляции, каждая граница — соглашение об именах, которое никто не проверяет. Deployment и Recovery уже реализованы на Python и имеют общую природу, поэтому они объединены в `txn`. `Build/Tests` — не часть времени выполнения.

Правило для Bash-модулей: **на верхнем уровне допустимы только определения** (функции и константы). Никакого кода, выполняющегося при подключении модуля. Единственная точка входа — `main`.

## 3. Сборка единого `rp.sh`

### 3.1. Текущее состояние (факты)

Источником истины сегодня является сам `rp.sh`, а `tools/embed-transaction.py` и `tools/embed-migration.py` вставляют в него код из `src/` между маркерами (в `rp.sh` это блоки `# BEGIN GENERATED MIGRATION HELPER` и аналогичный для транзакций). Python-код `rp.py` существует **только** внутри `rp.sh` (около `rp.sh:5643–6922`), в `src/` его копии нет. Встроенные `transaction.py` (`1264–1637`) и `migration.py` (`3015–3555`) побайтно равны файлам `src/` (проверено при составлении).

### 3.2. Предлагаемая схема

Инвертировать направление: `src/` → `tools/build.py` → `dist/rp.sh`.

1. `build.py` читает `VERSION` и `src/modules.list`, склеивает модули в порядке списка.
2. Python-пакет встраивается как набор вложений вида `<<'RP_PY_<ИМЯ>_EOF'`. Сборщик **падает**, если делимитер встречается внутри вложения.
3. Результат **детерминирован**: LF, без меток времени, фиксированная сортировка, одинаковый результат на двух машинах. Проверка: сборка дважды и сравнение `sha256`.
4. При установке вложения распаковываются в `/usr/local/lib/rp/py/rp/`; запуск: `python3 -I -B -m rp <команда>`. Флаг `-I` отсекает `PYTHONPATH` и пользовательские каталоги (важно для кода от root); `-B` не пишет `.pyc` туда, где их не должно быть. *Проверить:* работает ли `-m rp` с `-I` для пакета в нестандартном каталоге — нужен `PYTHONPATH`-эквивалент без `-I`, либо запуск через маленький `__main__`-файл по пути. Выбрать вариант, который проходит тест на Rocky 9 (Python 3.9) и 10.
5. Сборщик **отдельно выкладывает** каждое вложение файлом в `build/` для `shellcheck`, `bash -n` и `pyflakes`. Сегодня `static-check.py` вырезает их из `rp.sh` по маркерам; это нужно заменить.
6. CI проверяет: `dist/rp.sh` равен свежей сборке; релиз содержит `rp.sh`, `SHA256SUMS` и подпись (см. §6).

### 3.3. Что нельзя сломать

- `bash <(curl …)`: файл — непрокручиваемый поток. Это уже учтено: `self_source` (`rp.sh:3605`) при запуске через поток скачивает опубликованную версию заново, а комментарий об этом стоит у `rp.sh:3010–3012`. Сборка не должна полагаться на повторное чтение `$0`.
- `bash -n` на готовом `rp.sh` и на каждом сгенерированном скрипте (сторож, CLI).
- Размер: сейчас около 6925 строк; рост не критичен, но `self_ok` (`rp.sh:3560`) проверяет минимальный размер 32 КиБ и форму — убедиться, что новая проверка (§6) не противоречит ей.

## 4. Доказательство эквивалентности

Три механических проверки; ни одна не требует стенда.

### 4.1. Побайтное равенство первой сборки

Первый модульный коммит (T3) собирает `dist/rp.sh`, равный `rc.1` **байт в байт** с точностью до строки версии. Любое расхождение — остановка. Это доказывает, что при разрезании ничего не потеряно и не изменено.

### 4.2. Золотые файлы генераторов

Генераторы (`rp.py`, `vps2_files` в `rp.sh:1641`, `bundle`) не меняют систему, а пишут дерево файлов в каталог. Для набора фикстур `rp.conf` сохранить их вывод из `rc.1` в `tests/golden/` и сравнивать побайтно на каждом коммите.

Набор фикстур: все 15 непустых подмножеств четырёх транспортов; не менее двух вариантов SNI и двух вариантов DNS; 0 и 3 клиента; режим закрепления и авто. Секреты в фикстурах — фиксированные тестовые значения.

### 4.3. Манифест установленного состояния

`capture_runtime` (`rp.sh:3156`) уже снимает хэши, права, состояния юнитов, правила nft и маршруты для откатов. Вынести его в команду `rp state-manifest`. Процедура: на одном откатанном снимке установить `rc.1`, снять манифест; откатить снимок, установить сборку модульной версии, снять манифест; сравнить. Допустимое различие — только версия.

### 4.4. Поверхность CLI

Тест фиксирует список команд из `main` (`rp.sh:5596`) и вывод `rp help` (`usage`, `rp.sh:5530`). Изменение допускается только осознанно, с записью в `DECISIONS.md`.

## 5. Единый движок транзакций

### 5.1. Проблема

Сейчас два движка: `transaction.py` (VPS-2, `rp.sh:1264–1637`) и `migration.py` (VPS-1, `rp.sh:3015–3555`). У них десять одноимённых функций: `arm`, `atomic`, `command`, `digest`, `disarm`, `load`, `main`, `rollback`, `save`, `valid_member`. Построчно их различия **не проверены**; это первое, что нужно сделать в T4.

### 5.2. Порядок

1. Сравнить функции; для каждой записать: идентична / различается и почему.
2. Для различающихся — решение в `DECISIONS.md`; не «исправлять» разницу молча.
3. Объединить в `rp/txn.py` с параметризацией по роли; все тесты `test_transaction.py`, `test_migration.py`, `test_migrate_failures.py`, `test_update_lock.py` остаются и проходят без правок ожиданий.

### 5.3. Формат снимка

Сейчас откат самообновления, по словам отчёта о миграции, выполняет вспомогательный модуль **скачанного кандидата**, а не установленной версии. Это сознательное решение (схема снимка меняется между релизами), но защита от ошибок кандидата ослаблена: она настолько надёжна, насколько надёжен устанавливаемый код.

Предложение (не делать в T4; сначала записать решение): стабильный версионированный формат снимка — список путей, их содержимое, права и состояния — читаемый **любой** версией движка; восстановление выполняет установленная, давно испытанная версия. Кандидат только дополняет список своих путей. Требует отдельного обсуждения; в T4 только зафиксировать формат как `schema_version` снимка.

### 5.4. `fsync`

`conf_set` (`rp.sh:301`) заменяет файл через `mv`; в Python-части `fsync` файла и каталога выполняется, в Bash — нет. Низкий приоритет; решить явно и записать.

## 6. Канал обновления

### 6.1. Проблема (факты)

- `RP_URL` по умолчанию — `…/main/rp.sh` (`rp.sh:38`), а в `main` лежит старая 1.2.8.
- `self_ok` (`rp.sh:3560`) проверяет форму: размер, шебанг, заголовок, `bash -n`. Ни хэша, ни подписи нет.
- При обновлении на более старую версию выводится только предупреждение (`rp.sh:3684`), а вопрос по умолчанию принимается; без терминала `yesno` отвечает «да» сам.

### 6.2. Предложение

1. **Теги вместо `main`.** `RP_URL` указывает на релиз по тегу: `…/releases/download/vX.Y.Z/rp.sh`. Тег неизменяем.
2. **Подпись.** Релиз содержит `rp.sh`, `SHA256SUMS` и `SHA256SUMS.sig`. Открытый ключ Ed25519 встроен в `rp.sh`. Проверка средствами OpenSSL, без новых зависимостей: `openssl pkeyutl -verify -pubin -inkey rp.pub -rawin -in SHA256SUMS -sigfile SHA256SUMS.sig`. *Проверить* на OpenSSL из Rocky 9 и 10 (поддержка Ed25519 с `-rawin`).
3. **Запрет понижения.** Файл `schema_version` рядом с `rp.conf` и `clients.tsv`. Миграция вперёд автоматическая; запуск более старой версии поверх более новой схемы без явного `--allow-downgrade` отказывает. Без терминала `yesno` по умолчанию «нет» для понижения.
4. **Удалить `rp_gpt.sh`** из корня ветки до выпуска тега: это старая сборка со своим `RP_URL`.

### 6.3. Что остаётся честно

Подпись защищает от подмены файла на хостинге, но не от компрометации ключа владельца. Хранение закрытого ключа и порядок подписи — решение владельца; Codex его не принимает и не хранит ключ.

## 7. Права на VPS-2

Ключ VPS-1 на VPS-2 записан с `from=…,restrict,pty` (`rp.sh:2978`): это интерактивная оболочка root, и хост-ключ принимается как `accept-new` (`rp.sh:4366`). Компрометация VPS-1 в РФ означает root на VPS-2.

Предложение: заменить `pty` на `command=`-диспетчер с несколькими разрешёнными операциями (`push`, `test`, `diag`), а интерактивный вход оставить за отдельным ключом. *Решение владельца:* нужен ли интерактивный `rp ssh`. Менять только отдельным заданием с тестом, что транзакция `push` продолжает работать.

## 8. Teleport

### 8.1. Что показала проверка `deploy-teleport.sh`

Файл идентичен на `main` и в ветке (1486 строк, v1.1.4). Для использования как основы модуля он не подходит без переделки:

| № | Находка | Где в `deploy-teleport.sh` | Решение |
| --- | --- | --- | --- |
| 1 | Прокси слушает `0.0.0.0:443` (`web_listen_addr`). На VPS-1 Reality XHTTP по умолчанию тоже на TCP/443 (`RXH_PORT`, `rp.sh:3846`); `port_check` лишь отказывает, если порт занят, но после установки Teleport сам `rp` порт 443 занять не сможет | `1052`, `1097` | Отдельный порт для Teleport, не 443 и не 8443 (8443 занимают `RXH2_PORT` и `HY2O_PORT`). Прокси принимает произвольный `public_addr: хост:порт` |
| 2 | Скрипт предлагает сменить системный DNS, ставит собственный `dnscrypt-proxy` отдельным юнитом и drop-in для resolved/NetworkManager. На VPS-1 DNS принадлежит `rp` (DoH через туннель, fail-closed) | `42–47`, `319–570` | Вырезать целиком. Модуль не трогает DNS и время |
| 3 | Меню управления (админ, токен, сертификат, DNS, обновления, удаление) дублирует штатные средства Teleport | `1257–1486` | Модуль только устанавливает, обнаруживает существующее и печатает статус |
| 4 | Модель владения рассчитана на tar-архив; при установке RPM/DEB файл принадлежит пакету, а собственный юнит в `/etc/systemd/system/` затенит юнит пакета | `576`, `1078` | Использовать юнит пакета; добавлять только конфигурацию и drop-in |
| 5 | Подлинность пакета: SHA256 лежит в вашем же GitHub-релизе — это целостность, не подлинность | `743–816` | См. §8.4 |
| 6 | Встроенный ACME требует TCP/443; DNS-01 через `acme.sh` требует постоянно хранить токен API DNS и ставит сторонний код от root | `884–1020` | См. §8.5 |
| 7 | Вызывается `firewall-cmd --reload` | `1105` | `rp` пишет и в permanent, и в runtime (`rp.sh:360–370`), так что перезагрузка скорее безопасна; тест: правила и зоны `rp` не меняются |

### 8.2. Режим установки

Решение владельца определяет объём модуля. Два режима:

- **`join-only`** — VPS-1 и VPS-2 вступают как SSH-агенты в **существующий** кластер Teleport. Нет Auth, Proxy, сертификатов, порта 443, DNS. Модуль в несколько раз короче. **Рекомендуется как режим первого класса**: у владельца рабочий кластер уже есть.
- **`cluster`** — новый кластер на VPS-1: Auth, Proxy и SSH на VPS-1, SSH-агент на VPS-2. Нужен только если требуется второй кластер (второй CA, второй веб-интерфейс).

В `cluster` CA хранится на VPS-1 в российской сети: компрометация VPS-1 позволяет выпускать сертификаты для VPS-2. Включить MFA для администраторов.

### 8.3. Обнаружение существующей установки

Модуль **ничего не перезаписывает**. Признаки: `rpm -q teleport` / `dpkg -s teleport`, наличие `/etc/teleport.yaml`, `/var/lib/teleport`, `/usr/local/bin/teleport`, активный юнит `teleport.service`. Если что-то найдено — печатается статус и предлагается только `join-only`; в `cluster` остановка с пояснением.

### 8.4. Источник и проверка пакетов

Пакеты: `teleport-18.11.13-1.x86_64.rpm` (Rocky/RHEL) и `teleport_18.11.13_amd64.deb` (Debian/Ubuntu) из вашего релиза `teleport-v18.11.13`. Версия — в `teleport.meta`, не в логике.

По документации Teleport для прямой загрузки пакетов предусмотрены файл `.sha256` рядом с пакетом и проверка `sha256sum --check`; репозитории apt/yum подписаны GPG, а для RHEL 10 yum-репозитория нет. Подписан ли сам RPM и как его проверить `rpm -K`, **я не подтвердил** — проверить по документации и фактическому пакету.

Предложение: пакет принимается, только если совпали **оба** хэша — зашитый в `teleport.meta` и полученный со страницы производителя (если доступна; если CDN производителя недоступен из РФ — только зашитый). Расхождение останавливает установку. `dnf` не должен обновлять Teleport сам: версия задаётся метаданными (`versionlock` или отсутствие подключённого репозитория).

### 8.5. Сертификаты

- При нестандартном порте встроенный ACME (TLS-ALPN) обычно неприменим.
- DNS-01 требует токена DNS и стороннего клиента — противоречит принципу «без лишних секретов».
- **По умолчанию:** самоподписанный сертификат прокси и закрепление `ca_pin` на агентах. Публичный сертификат — осознанный выбор владельца, отдельным путём.

### 8.6. Регистрация VPS-2 без постоянных секретов

Сейчас токен печатается на экран; на VPS-2 его пришлось бы вводить руками через консоль хостера. Предложение (команды **проверить по документации Teleport 18.x**):

1. `rp` на VPS-1 создаёт токен узла со сроком 10–15 минут (`tctl tokens add --type=node --ttl=15m`).
2. Токен и отпечаток CA передаются на VPS-2 по уже существующему аутентифицированному каналу `rp push` и хранятся только в `/run` с правами `0600`.
3. Агент вступает в кластер (`proxy_server`, `auth_token`, `ca_pin`).
4. `rp` удаляет токен (`tctl tokens rm`) и проверяет, что узел виден (`tctl nodes ls`).
5. На диске VPS-2 остаётся только собственная идентичность агента в `/var/lib/teleport`, и она штатная.

Связь `rp` и Teleport существует только в момент регистрации.

### 8.7. Условия независимости (каждое — тест)

- между юнитами `rp` и Teleport нет `Requires`, `BindsTo`, `PartOf`;
- откат и удаление `rp` работают по **явным** спискам путей и не затрагивают `/etc/teleport*`, `/var/lib/teleport`, `/usr/local/bin/{teleport,tctl,tsh,tbot}` (в `BASE_PATHS`, `rp.sh:1292`, этих путей нет — сохранить);
- отдельный порт и отдельные записи firewalld, помеченные комментарием;
- агент VPS-2 подключается к прокси **напрямую**, а не через внутренний WG;
- модуль не вызывается при запуске `rp`, только по явному выбору пользователя; по умолчанию выключен;
- ядро (`core`, `system`, `net`, `roles`, `txn`, `cli`) после T7 не меняется.

### 8.8. Оборотная сторона независимости

Раз агент VPS-2 соединяется напрямую, он идёт **обычным TLS** с IP, который блокируется, и не получает защиты транспортов `rp`. Сценарии из `TSPU-RESISTANCE.md` (заморозка потока и т.п.) могут влиять и на него. Не обещать доступ к VPS-2 через Teleport, пока это не проверено. Независимым каналом остаётся консоль хостера (если она у вас есть); Teleport её не заменяет.

## 9. Привязка приёмки к модулям

Сборщик записывает хэш каждого модуля. Результаты приёмки привязываются к хэшам модулей, которые они покрывают. Если хэши `net`, `txn`, `roles` не изменились, а изменился только `integrations/teleport`, то приёмка ядра остаётся действительной, и достаточны тесты Teleport и невмешательства. Правка в `net` или `txn` возвращает полную регрессию. Это делает правило «любое влияющее изменение требует повторной приёмки» исполнимым.
