# rp: WireGuard → VPS-1 → обратный туннель → VPS-2

Первый предварительный релиз: **1.2.9-lab.23**, канал **Pre-release**.
[Скачать скрипт и контрольные суммы](https://github.com/fLex0id/reverse-proxy/releases/tag/v1.2.9-lab.23).
Полная приёмка продолжается; готовность к работе 24/7 пока не заявлена.
Шестичасовой прогон отложен оператором. [Изменения и ограничения](reports/RELEASE_NOTES_RU.md).
Актуальные результаты: [STATUS](reports/STATUS.md),
[матрица приёмки](reports/ACCEPTANCE.json), [справка](reports/WORK_SUMMARY_RU.md).

Существующая архитектура сохраняется: клиент подключается к WireGuard на VPS-1,
а зарубежный трафик проходит через VPS-2. Российские ресурсы направляются
напрямую с VPS-1 по предусмотренным правилам. Доступны четыре транспорта:
REALITY/XHTTP packet-up, REALITY/XHTTP stream-up, Hysteria2 и Hysteria2 с Salamander.
Ручная фиксация транспорта отключает автоматическое переключение на резерв.

## Стенд и границы проверки

Обе серверные роли испытываются на Rocky Linux 10.2; Debian 13 используется
для изолированных WireGuard-клиентов и управления тестами. Rocky 9 и серверные
роли на других системах не следует считать проверенными по этим результатам.
Стенд находится в одной LAN и сам использует внешний VPN. Совпадение внешнего
IP серверов не доказывает правильный маршрут: для этого анализируются пакеты.
Результаты лаборатории не являются гарантией устойчивости к реальному ТСПУ.

## Получение проверяемой сборки

Разработка ведётся в `codex/rp-24x7-lab`. `main` и резервная ветка не меняются.
Следующие команды получают конкретный кандидат, а не объявленный стабильный релиз:

```bash
RP_RELEASE_COMMIT=c8ba2c74caee60bb19e6b778c5416c1457c7c5d9
RP_RELEASE_SHA256=2d6e6d7962c4d02a9c8f0b39a463265efd8419d29dec9a2accf00b6e722a5095
curl -fsSL "https://raw.githubusercontent.com/fLex0id/reverse-proxy/$RP_RELEASE_COMMIT/rp.sh" -o rp.sh
printf '%s  rp.sh\n' "$RP_RELEASE_SHA256" | sha256sum -c -
```

При несовпадении SHA256 файл не запускают. Для запуска из потока и обновления
нужно явно указать `RP_URL` нужной сборки: до принятия релиза стандартный URL
из `main` может содержать другую версию. Сохранение поточной сборки проверяет
совпадение версии с повторно скачанным файлом.

## Установка

1. Сохраните независимый SSH-доступ или консоль к обеим выделенным машинам.
   На VPS-1 запустите `bash rp.sh install` от root, выберите роль VPS-1,
   адрес, клиентский порт WireGuard и нужные транспорты. Подтвердите настройки
   после проверок SNI. Пиннутые версии компонентов задаются самим скриптом.
2. На VPS-1 выполните `rp link`. Введите выданную команду на VPS-2 от root.
   Она проверяет ключ HTTPS-сервера и получает одноразовый установочный блок.
   По умолчанию ссылка действует 30 минут. Вывод содержит доступ к секретному
   блоку и не предназначен для публикации.
3. Если VPS-2 не может получить ссылку, используйте `rp block`. Вставьте файл
   или все части по порядку через консоль VPS-2. Контрольная сумма проверяется
   до запуска; ошибка последней части сохраняет код ошибки установщика.
4. Дождитесь полных T1–T3 каждого настроенного транспорта. На VPS-1 проверьте
   `rp transports`, `rp tunnel status` и `rp test`. Успех отдельного транспорта
   не заменяет полный результат.
5. Добавьте клиента: `rp client add laptop`. Конфигурация и QR выводятся командой;
   файл сохраняется в `/root/rp-clients/laptop.conf` с правами `0600`.
   Проверьте с клиента HTTPS, DNS и требуемые приложения.

Приёмочная установка с нуля на лабораторных машинах проводится после отдельного
сообщения оператору об очистке. Она ещё не считается выполненной.

## Повседневное управление

| Задача | Команда |
|---|---|
| Меню; текстовый режим | `rp`; `rp --ascii` |
| Клиенты | `rp client list`, `rp client show laptop`, `rp client del laptop` |
| Автоматическое переключение | `rp tunnel auto` |
| Ручной транспорт | `rp tunnel reality-xhttp2`, `reality-xhttp`, `hy2-wg` или `hy2o-wg` |
| Согласование состояния | `rp tunnel status`, `rp tunnel sync` |
| DNS | `rp dns show`, `rp dns test`, `rp dns set quad9 cloudflare` |
| Правила РФ | `rp ru status`, `rp ru update`, `rp ru proxy ДОМЕН`, `rp ru direct ДОМЕН`, `rp ru del ДОМЕН` |
| Диагностика | `rp status`, `rp doctor`, `rp diag`, `rp logs 80` |
| Проверки с явным перезапуском | `rp test --long --restart` |

`rp diag --fix` меняет состояние для исправления ошибок. `rp restart` проверяет
готовность служб после перезапуска. Ошибки записи/применения возвращают ненулевой
код; при неудавшемся восстановлении сохраняется резервная копия и её путь.
Меню и изменяющие команды используют общую блокировку операций.

## Обновление и восстановление

На VPS-1 скачайте требуемый файл с проверкой SHA256 и выполните `bash rp.sh migrate`
либо используйте `RP_URL=URL_НУЖНОЙ_СБОРКИ rp update`. Миграция сохраняет управляемое
состояние, проверяет локальную готовность и откатывается при ошибке или прерывании.
Повторить незавершённое восстановление можно командой `rp migrate-recover`.

Для обновления VPS-2 выполните `rp push` с VPS-1. Подтверждение происходит после
полных T1–T3 всех транспортов, согласования маршрута и проверки выхода.
Ожидаемый итог — `FULL_OK` и сообщение о подтверждении. Неподтверждённое обновление
имеет штатный 30-минутный откат. Проверки и таймер нельзя отключать ради успеха.

Если внешний VPN изменил адрес выхода, прежний отпечаток может остановить
подтверждение, даже когда приложения работают. Сначала сверяют выход через
туннель и непосредственно на VPS-2 через независимый управляющий доступ;
несовпадение нельзя автоматически объявлять исправностью или утечкой.

`rp uninstall` удаляет установку VPS-1 после подтверждения, отдельно предлагая
удаление настроек. На VPS-2 используется `rp remove`. Ключи независимого доступа
и чужие unit-файлы должны сохраняться. Полная приёмка удаления на чистом стенде
отмечается отдельно в матрице.

## Воспроизводимость

```bash
python3 -m unittest discover -s tests -q
python3 tools/static-check.py
```

Статические проверки требуют Bash, ShellCheck, Python 3 и pyflakes.
Живые сценарии описаны в [lab/README.md](lab/README.md); они предназначены для
выделенного стенда. Исходные конфигурации, ключи и захваты хранятся в исключённых
из Git каталогах `lab/private` и `lab/artifacts`. В `reports/results` публикуются
результаты без секретов. Старые неудачные прогоны сохраняются рядом с исправленными.
